# PersistRank: Duration-Aware Alert Prioritization for Microservice Anomalies

PersistRank is a research framework that improves alert prioritization in cloud-native microservice architectures by incorporating **temporal persistence** — how long a service has remained in a degraded state — alongside traditional anomaly severity and business criticality signals.

## Motivation

Traditional alert prioritization treats all anomalies equally regardless of duration. This causes engineers to investigate transient spikes (e.g., a brief CPU burst) before persistent faults (e.g., a slow memory leak), wasting valuable incident response time. PersistRank addresses this by tracking consecutive anomalous time windows per service and folding that signal into a multiplicative risk score.

## Risk Model

```
Risk(v, t) = Anomaly_Severity(α) × Business_Criticality(γ) × Temporal_Persistence(π)
```

All three factors must be elevated for a service to rank highly, reducing false urgency from single-signal spikes.

## Key Results

| Method | P@1 | P@3 | P@5 |
|--------|-----|-----|-----|
| AlertRank (baseline) | — | 0.442 | — |
| **PersistRank (ours)** | — | **0.514** | — |

**+7.2 percentage points** improvement in Precision@3 over the baseline.

Largest gains by anomaly type:
- Response-time delays: **+18.9 pp**
- Out-of-order packets: **+13.3 pp**
- Low-bandwidth conditions: **+11.2 pp**

Ablation study confirms that removing persistence alone reduces P@3 by **14.0%**, validating it as an independent, complementary signal.

## Dataset

Evaluated on the **RS-Anomic** benchmark — a publicly available dataset collected from a 12-service Robot Shop e-commerce demo running on Kubernetes, with 14 fault-injection scenarios across 10 anomaly types. Metrics are collected via cAdvisor (19 metrics per service, 30-second windows).

**Monitored services and business criticality (1–5 scale):**

| Service | Criticality | Role |
|---------|:-----------:|------|
| payment | 5 | Payment processing — direct revenue loss |
| cart | 4 | Shopping cart — checkout pipeline |
| shipping | 3 | Shipping cost calculation |
| dispatch | 3 | Order dispatch via message queue |
| web | 3 | Front-end nginx proxy |
| user | 3 | User authentication & accounts |
| mongodb | 3 | Database for cart, user, ratings |
| rabbitmq | 2 | Message broker |
| mysql | 2 | Database for shipping service |
| redis | 2 | Session cache |
| catalogue | 1 | Product listing (browsing only) |
| ratings | 1 | Product ratings (cosmetic feature) |

## Project Structure

```
ebision2026/
├── load_data.py          # Phase 1 — Load & normalize RS-Anomic data
├── anomaly_score.py      # Phase 3 — Train Isolation Forest on normal data
├── per_service.py        # Phase 4 — Per-service anomaly scores (MAD)
├── criticality.py        # Phase 5 — Static business criticality lookup
├── persist.py            # Phase 6 — Compute temporal persistence scores
├── risk_score.py         # Phase 7 — Combine α × γ × π into risk scores
├── eval.py               # Phase 8 — Precision@K evaluation + ablation
├── figures.py            # Phase 9 — Generate publication-ready figures
├── isolation_forest.joblib  # Serialized trained model
├── scaler.joblib            # Serialized StandardScaler
├── rs-anomic/               # Raw benchmark data (normal + anomaly scenarios)
└── results_main.csv         # Evaluation output
```

> Large intermediate CSV files (`processed_data.csv`, `scored_data.csv`, etc.) are excluded from the repository via `.gitignore` and must be regenerated by running the pipeline.

## Pipeline

Run the scripts in order to reproduce all results:

```bash
python load_data.py        # → processed_data.csv (123,751 rows × 231 cols)
python anomaly_score.py    # → scored_data.csv + trained model files
python per_service.py      # → per_service_data.csv
python persist.py          # → persistence_data.csv
python risk_score.py       # → risk_data.csv
python eval.py             # → results_main.csv, results_per_type.csv
python figures.py          # → fig2–fig7 PNG (300 DPI)
```

## Implementation Details

| Component | Detail |
|-----------|--------|
| Anomaly detector | Isolation Forest (`n_estimators=100`, `contamination=0.05`) |
| Training data | Normal operating data only (~7,500 windows) |
| Features | 228 (19 metrics × 12 services) |
| Anomaly threshold | 75th percentile of per-service scores on normal data |
| Persistence cap (κ) | 10 consecutive windows |
| Evaluation metric | Precision@K (K = 1, 3, 5) |
